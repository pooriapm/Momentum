# Momentum — Phase 0 Product Contract

Version: 0.7
Status: Founder-approved product baseline
Last reviewed: 2026-08-17
Scope: Product, business, safety, and design logic only. No production-code implementation is authorized by this document. D1–D13 are closed.

## 1. تعریف یک‌خطی محصول

Momentum برای بزرگسالان یک برنامهٔ یکپارچهٔ تمرین و تغذیه می‌سازد، آن را پس از اعتبارسنجی به‌صورت خودکار وارد محصول می‌کند و از ثبت عملکرد کاربر برای ساخت برنامهٔ ماه بعد استفاده می‌کند.

Momentum چت، پیام‌رسان، prompt مکالمه‌ای یا شخصیت «مربی هوش مصنوعی» ندارد. پیش از چرخه جدید، کاربر می‌تواند یک یادداشت اختیاری و محدود برای تغییرات برنامه بعد ثبت کند.

## 2. تصمیم‌های غیرقابل مذاکره

1. هر کاربر در هر چرخهٔ ماهانه فقط یک فراخوانی هوش مصنوعی دارد.
2. همان فراخوانی باید برنامه کامل یک ماه و هر دو بخش تمرین و تغذیه را در یک خروجی نسخه‌بندی‌شده برگرداند.
3. خروجی قبل از نمایش، با قواعد قطعی ایمنی و ساختار داده اعتبارسنجی می‌شود.
4. خروجی معتبر بدون copy/paste کاربر به برنامه وارد می‌شود.
5. ثبت غذا، تمرین، وزن، گزارش هفتگی اختیاری، چک‌این روزانهٔ کم‌رنگ اختیاری، یادداشت چرخه بعد یا تغییر تنظیمات در میانه ماه هیچ فراخوانی AI ایجاد نمی‌کند.
6. تغییرات میانه ماه ذخیره می‌شوند و در snapshot ماه بعد استفاده خواهند شد.
7. ماه دوم و همه ماه‌های بعد فقط پس از تأیید اشتراک فعال ساخته می‌شوند.
8. شکست provider، validation یا import برنامهٔ قبلی را حذف یا خراب نمی‌کند.
9. هر چرخه حداکثر یک برنامهٔ واردشدهٔ موفق دارد. تا قبل از import، job در صف است؛ خطای گذرا پس از تأخیر دوباره تلاش می‌شود. اگر انتظار از ۳ دقیقه بیشتر شد کاربر خطا می‌بیند و می‌تواند دوباره درخواست بدهد. اگر همان job هنوز زنده است، درخواست کاربر وضعیت را می‌خواند نه call دوم. پس از import موفق هیچ فراخوانی دیگری در آن چرخه نیست.
10. `product_region` نسخهٔ محصول را قفل می‌کند: `ir` یعنی رابط فارسی و قیمت ریالی؛ `intl` یعنی رابط انگلیسی و قیمت دلاری. تقویم، واحدها و فرهنگ غذایی تنظیمات جدا می‌مانند و با تغییر IP عوض نمی‌شوند.
11. اصطلاحات فنی مربوط به جهت نوشتار در رابط کاربر نمایش داده نمی‌شوند.
12. طراحی محصول از اصول Apple HIG برای وضوح، سلسله‌مراتب، کنترل‌های آشنا، فضای تنفس و عمق محدود پیروی می‌کند و هویت مستقل Momentum را حفظ می‌کند.

## 3. تعریف چرخه برنامه

`Plan Cycle` یک بازهٔ خدماتی ماهانه است و با `Billing Period` یکسان نیست.

- اشتراک MVP ماهانه است: هر دورهٔ پرداخت موفق، حق یک برنامهٔ یک‌ماهه می‌دهد.
- همان برنامه برای حدود یک ماه تقویمی در timezone کاربر، روزبه‌روز نمایش داده می‌شود. AI در میانهٔ ماه فراخوانی نمی‌شود.
- بستهٔ سالانه (یک پرداخت = دوازده چرخه) در MVP نیست.
- هر چرخه شناسه، تاریخ شروع، تاریخ پایان، وضعیت entitlement، snapshot ورودی، job تولید، نسخه خروجی و وضعیت import مستقل دارد.
- مرجع زمان، timezone ذخیره‌شدهٔ کاربر و محاسبهٔ server-side است.

## 4. چرخه ماه اول

1. کاربر حساب را تأیید و onboarding را کامل می‌کند.
2. consent، eligibility و safety gate بررسی می‌شوند. ریجن محصول دیوار جغرافیایی نیست.
3. اطلاعات پایه به یک snapshot ساختاریافته و حداقلی تبدیل می‌شود.
4. برای چرخه اول فقط یک generation job رزرو می‌شود.
5. کاربر صفحهٔ انتظار واحد را می‌بیند. می‌تواند صفحه را ببندد. اگر پس از ۳ دقیقه آماده نشد، خطا و دکمهٔ تلاش دوباره نشان داده می‌شود تا گیر نکند.
6. درخواست در صف سرور است. بک‌اند یک prompt می‌فرستد؛ مدل خروجی ترکیبی یک‌ماهه برمی‌گرداند. خطای گذرا با تأخیر دوباره در صف تلاش می‌شود و کاربر همان خطای قابل‌فهم را می‌بیند.
7. خروجی از schema، catalog، allergy، safety عبور می‌کند و در صورت اعتبار به‌صورت خودکار import می‌شود.
8. وقتی آماده شد، نمای روزانهٔ همان ماه نمایش داده می‌شود. ریرایت فلوهای قبل از این نقطه را اصلاح می‌کند.

## 5. چرخه ماه دوم و ماه‌های بعد

1. قبل از ساخت، اشتراک فعال و entitlement همان چرخه در سمت سرور تأیید می‌شود.
2. snapshot جدید از این منابع ساخته می‌شود:
   - داده پایه و رضایت‌های معتبر onboarding؛
   - آخرین پروفایل و هدف تأییدشده؛
   - نسخه برنامه ماه قبل؛
   - میزان انجام تمرین‌ها و وعده‌ها؛
   - گزارش‌های عمومی هفتگی؛
   - سیگنال‌های ایمنی و داده‌های ترکیب بدنی تأییدشده.
3. داده خام غیرضروری، transcript یا prompt کاربر وجود ندارد.
4. یک generation job جدید برای چرخه جدید رزرو می‌شود.
5. برنامه معتبر جدید import و از تاریخ شروع چرخه فعال می‌شود.
6. برنامه قبلی به‌عنوان history فقط‌خواندنی باقی می‌ماند.

### ورودی اختیاری کاربر برای چرخه بعد

نزدیک پایان ماه کاربر فقط مطلع می‌شود که برنامهٔ جاری تمام می‌شود. نقطهٔ فهم، **آخرین گزارش هفتگی** است: بعد از ثبت آن مشخص می‌شود برنامه بعد چیست و اگر هنوز روی هدیه/پلن رایگان است باید اشتراک ماهانه را شروع کند. بیشتر کاربران از هدیهٔ D1 به این نقطه می‌رسند؛ پس checkout از همین‌جا شروع می‌شود (PROG-07 → LIFE-08).

یادداشت اختیاری چرخه بعد (PROG-07) می‌ماند. اگر اقدامی نکند، پس از پرداخت موفق snapshot از onboarding، اجرا و گزارش‌های هفتگی ساخته می‌شود.

## 6. رفتار میانه ماه

- کاربر برش همان روز را اجرا می‌کند (وعده، تمرین، خرید).
- چک‌این روزانه اختیاری است و در UI کم‌رنگ است؛ مسیر اصلی Today نیست.
- گزارش هفتگی هم اختیاری است اما برجسته است.
- هیچ‌کدام AI صدا نمی‌زنند و برنامه جاری را عوض نمی‌کنند.
- جایگزینی غذا یا حرکت فقط از catalog قطعی است.

## 7. وضعیت‌های اشتراک و خطا

| وضعیت | رفتار محصول |
| --- | --- |
| اشتراک فعال | چرخه بعد در زمان مقرر واجد تولید است |
| در انتظار تأیید پرداخت | generation شروع نمی‌شود؛ وضعیت روشن نمایش داده می‌شود |
| اشتراک منقضی/لغوشده | generation جدید شروع نمی‌شود؛ برنامه ذخیره‌شده طبق سیاست دسترسی قابل مشاهده می‌ماند |
| provider / timeout / صف ناموفق قبل از import | خطا به کاربر؛ تلاش خودکار در صف؛ دکمهٔ تلاش دوباره؛ برنامه قبلی اگر باشد سالم می‌ماند |
| import موفق | سهم چرخه مصرف شده؛ call دیگر در این ماه نیست |
| validation ناموفق | خروجی import نمی‌شود؛ برنامه قبلی حفظ می‌شود |
| import ناموفق | نسخه جدید فعال نمی‌شود و عملیات قابل بازیابی ثبت می‌شود |
| product region `ir` یا `intl` | همان محصول؛ فقط زبان پیش‌فرض و ارز فهرست فرق دارد. generation و checkout در هر دو نسخه فعال‌اند |
| safety blocked | generation خودکار انجام نمی‌شود و راهنمای مناسب نمایش داده می‌شود |

## 8. معماری اطلاعات MVP

چهار مقصد اصلی محصول:

1. **امروز:** اقدام‌های روز، وعده بعدی، تمرین بعدی و وضعیت برنامه ماه جاری.
2. **برنامه:** نمای روز/هفته/ماه از برنامه تمرین، تغذیه و خرید.
3. **پیشرفت:** پایبندی روزها، گزارش هفتگی عمومی، و آمادگی ماه بعد.
4. **حساب من:** هویت، پروفایل/ترجیحات، اشتراک، خروجی یا حذف حساب، ظاهر، زبان، نصب برنامه (فقط اگر نصب نشده)، و خروج. برچسب بازاری «Private» در UI نیست.

هیچ مقصد، tab، صفحه، composer یا notification با مفهوم چت یا مربی AI وجود ندارد.

## 9. قرارداد بسته تجاری

- MVP یک اشتراک پولی واحد دارد و در هر چرخه ماهانه حداکثر یک برنامه کامل ارائه می‌کند.
- تعداد فراخوانی استفاده‌نشده ذخیره یا منتقل نمی‌شود.
- دسترسی به برنامه خریداری‌شده، export داده، حقوق حریم خصوصی و راهنمای ایمنی با quota مسدود نمی‌شود.
- بسته‌های بیشتر فقط پس از اثبات یک ارزش غیر AI مستقل مانند گزارش‌های پیشرفته یا integration بررسی می‌شوند.
- قیمت اشتراک یک hypothesis بیزینسی است و قبل از پرداخت واقعی نیازمند آزمایش بازار و تأیید حقوقی است.

## 10. تصمیم‌های تأییدشده بنیان‌گذار

### D1 — برنامه هدیه ماه اول با سقف بودجه داینامیک — تأیید شد

اولین برنامه کامل ماهانه برای هر کاربر واجد شرایط هدیه است، تا زمانی که بودجه فعال کمپین رایگان ظرفیت داشته باشد. این تصمیم با یک کانفیگ server-owned و قابل تغییر بدون انتشار نسخه جدید کنترل می‌شود.

کانفیگ حداقل شامل این موارد است:

- فعال/غیرفعال بودن هدیه برنامه اول؛
- سقف کل بودجه کمپین به دلار؛
- هزینه رزروی محافظه‌کارانه هر برنامه؛
- تاریخ شروع و پایان اختیاری کمپین؛
- بازارهای مجاز؛
- حداقل بودجه باقیمانده لازم برای پذیرش کاربر بعدی؛
- رفتار پس از پرشدن سقف.

قبل از generation، سیستم به‌صورت اتمیک هزینه رزروی برنامه را از ظرفیت باقی‌مانده کم می‌کند. اگر ظرفیت کمتر از هزینه رزروی باشد، job رایگان ساخته نمی‌شود. پس از پایان job، مبلغ رزروی با هزینه واقعی reconciliation می‌شود. اگر failure پیش از شروع provider باشد reservation آزاد می‌شود؛ پس از شروع provider هیچ call دوم در همان چرخه مجاز نیست.

پس از پرشدن سقف:

- کاربران جدید دیگر برنامه واقعی رایگان دریافت نمی‌کنند؛
- Preview نمایشی و مسیر خرید اشتراک در صورت مجازبودن بازار باقی می‌ماند؛
- کاربری که هدیه‌اش قبلاً رزرو شده، حق خود را از دست نمی‌دهد؛
- برنامه‌های هدیه قبلی قابل مشاهده می‌مانند؛
- افزایش بودجه یا فعال‌سازی دوباره فقط برای کاربران واجد شرایطی اعمال می‌شود که قبلاً هدیه نگرفته‌اند.

هر شخص حداکثر یک هدیه برنامه اول دارد. ساخت حساب جدید، replay یا تغییر دستگاه هدیه تازه ایجاد نمی‌کند. جزئیات تشخیص سوءاستفاده باید با حداقل‌سازی داده و بررسی حریم خصوصی طراحی شود.

### D2 — مرز زمانی چرخه — تأیید شد

چرخه rolling است و از زمان import موفق برنامه اول آغاز می‌شود؛ به ابتدای ماه میلادی یا شمسی وابسته نیست.

### D3 — دسترسی پس از لغو — تأیید شد

برنامه‌های قبلاً تولیدشده و history برای کاربر قابل مشاهده باقی می‌مانند، اما هیچ چرخه یا generation جدید ایجاد نمی‌شود.

### D4 — بسته‌بندی MVP — تأیید شد

MVP فقط یک اشتراک پولی دارد. نام‌ها و سطوح Core/Pro در MVP وجود ندارند؛ بسته بیشتر فقط پس از اثبات ارزش غیر AI مستقل بررسی می‌شود.

### D5 — زمان و ورودی برنامه ماه بعد — تأیید شد

برنامه ماه بعد زودتر از موعد تولید نمی‌شود. در پایان چرخه و پس از تأیید اشتراک ماهانه، همان یک فراخوانی ماهانه دوباره اجرا می‌شود و کاربر همان صفحهٔ انتظار D13 را می‌بیند. ورودی اصلی میانهٔ ماه، گزارش عمومی هفتگی است. اگر کاربر در پایان ماه اقدامی نکند، snapshot از onboarding، پروفایل، اجرای روزها و گزارش‌های هفتگی ساخته می‌شود.

یک یادداشت آزاد محدود در کنار فیلدهای ساختاریافته مجاز است. این یادداشت فقط ورودی یک‌باره چرخه بعد است، پاسخ جداگانه نمی‌گیرد و هیچ chat یا conversation ایجاد نمی‌کند. محدودیت دقیق طول در فاز طراحی فرم تعیین می‌شود.

**تصمیم طراحی فرم:** یادداشت اختیاری حداکثر ۵۰۰ نویسه است، شمارنده نرم از
۴۰۰ نویسه نمایش داده می‌شود، newline و ارقام هر دو زبان پذیرفته می‌شوند و هیچ
داده سلامت غیرضروری یا دستور برای دورزدن safety مجاز نیست. مقدار خالی یعنی مسیر
پیش‌فرض carry-forward و هیچ call یا پاسخ جداگانه‌ای ایجاد نمی‌کند. مقدار پیش از
ورود به snapshot در سمت سرور trim، length-check و safety-check می‌شود و در
analytics عمومی ثبت نمی‌شود.

### D6 — تحلیل گزارش ترکیب بدنی — تأیید شد

هر کاربر در کل چرخه فقط یک AI call دارد و آن call برای تولید برنامه کامل ماهانه است. گزارش ترکیب بدنی با AI جداگانه تحلیل نمی‌شود. مقادیر لازم پیش از generation به‌صورت دستی یا ابزار غیرمولد استخراج و توسط کاربر تأیید می‌شوند؛ فقط مقادیر تأییدشده وارد همان درخواست واحد ماهانه خواهند شد.

### D7 — قیف عمومی self-serve — تأیید شد ۲۰۲۶-۰۸-۱۶

هر کس می‌تواند ثبت‌نام کند. دعوت‌نامه یا waitlist مسیر پیش‌فرض نیست. اولین برنامهٔ کامل ماهانه همان هدیهٔ D1 است تا وقتی بودجهٔ کمپین ظرفیت داشته باشد. پس از پایان آن چرخه، ادامه فقط با اشتراک پولی واحد است.

کاربر هدفِ عرضه: بزرگسالان ۱۸+ در هر دو نسخهٔ محصول (`ir` و `intl`). دیوار «در دسترس نیست» برای ایران وجود ندارد.

### D8 — روش پرداخت قبل از generation — تأیید شد ۲۰۲۶-۰۸-۱۶

قبل از اولین فراخوانی provider، کاربر روش پرداخت را با SetupIntent یا مجوز صفر ثبت می‌کند. کارت تا چرخهٔ دوم شارژ نمی‌شود. `admin_review` فقط استثنای پشتیبانی است. کشور صورتحساب پردازنده برای تسویه و مالیات بعدی است، نه برای بستن AI. IP فقط یک‌بار در ساخت حساب `product_region` را می‌نویسد و بعداً آن ستون را عوض نمی‌کند.

### D9 — پرداخت نازک پیش‌نیاز generation است — تأیید شد ۲۰۲۶-۰۸-۱۶

فاز ۵ نقشه راه قبلاً همهٔ پرداخت را تا پس از retention عقب می‌انداخت و D7 را غیرممکن می‌کرد. تفکیک:

- **۵الف** همراه فاز ۳: جمع‌آوری روش پرداخت، شارژ چرخهٔ دوم، لغو؛
- **۵ب** بعدتر: مالیات، dunning، آزمایش منطقه‌ای و پرداخت‌نامه.

### D10 — catalog نسخهٔ ۲ دروازهٔ generation است — تأیید شد ۲۰۲۶-۰۸-۱۶

`momentum-core@v1` (۳ غذا، ۴ حرکت، ۲ آلرژن) seed آزمایشی است نه محصول. generation عمومی تا وجود `momentum-core@v2` بازبینی‌شده شروع نمی‌شود. شخصی‌سازی یعنی شناسه‌های catalog متفاوت برای محدودیت‌های متفاوت، نه نثر متفاوت حول همان وعده‌ها.

### D11 — غربال زودهنگام؛ آلرژی از فهرست کنترل‌شده — تأیید شد ۲۰۲۶-۰۸-۱۶

سن، بارداری، اختلال خوردن و شرایط پرخطر بعد از Basics و قبل از رضایت دادهٔ سلامت، غذا، تمرین و بدن اجرا می‌شوند. آلرژی‌ها multi-select از catalog آلرژن هستند نه متن آزاد که در generation با ۴۰۹ شکست بخورد. اگر کاربر نتواند به catalog نگاشت کند، generation در onboarding با مسیر انسانی مسدود می‌شود. کشور محل سکونت خوداظهاری است و دروازهٔ AI نیست؛ نسخهٔ محصول از `product_region` می‌آید (D12).

ترتیب هشت step (همان ۱۳۲ شناسه): Basics → Health → Consent → Goal → Food → Training → Body → Review.

### D12 — دو نسخهٔ محصول از روی ریجن پایدار حساب — تأیید شد ۲۰۲۶-۰۸-۱۶

تنها تفاوت ریجن‌ها زبان پیش‌فرض و ارز فهرست قیمت است. محدودیت جغرافیایی دیگری در محصول نیست.

- بازدیدکنندهٔ ناشناس با IP ایران نسخهٔ فارسی و قیمت ریالی می‌بیند (`product_region` موقت `ir`).
- بازدیدکننده با IP غیر ایران نسخهٔ انگلیسی و قیمت دلاری می‌بیند (`intl`).
- در ساخت حساب، همان مقدار روی `profiles.product_region` ثبت و قفل می‌شود. منبع `ip_at_signup` یا اصلاح `admin` است. IP بعدی، VPN و کشور خوداظهاری این فیلد را عوض نمی‌کنند.
- حساب `ir` همیشه فارسی + IRR می‌ماند حتی اگر بعداً از آلمان باز شود. حساب `intl` همیشه انگلیسی + USD می‌ماند حتی اگر بعداً از ایران باز شود.
- generation، هدیهٔ D1، checkout و ایمنی در هر دو نسخه یکسان‌اند. صفحهٔ «در این منطقه در دسترس نیست» وجود ندارد.
- IP خام ذخیره نمی‌شود. `geo-context` برای کاربر واردشده همان `product_region` قفل‌شده را برمی‌گرداند.

### D13 — برنامه یک‌ماهه، انتظار با صف و تایم‌اوت، گزارش هفتگی برجسته — تأیید شد ۲۰۲۶-۰۸-۱۶

پس از onboarding یک برنامهٔ یک‌ماهه با یک job ساخته می‌شود. در میانه ماه AI نیست.

- اشتراک MVP فقط ماهانه است.
- صفحه انتظار: «لطفاً منتظر بمانید. برنامه شخصی‌سازی‌شده شما در حال تولید است.» متن چرخشی، انیمیشن، نوار پیشرفت نمایشی. ترک صفحه مجاز است.
- درخواست در صف است. خطای گذرا بعد از تأخیر دوباره تلاش می‌شود. اگر پس از ۳ دقیقه آماده نشد، کاربر خطا می‌بیند و می‌تواند دوباره درخواست بدهد. job زنده تکراری ساخته نمی‌شود.
- پس از import، Today/Plan برش روزانه را نشان می‌دهند.
- چک‌این روزانه اختیاری و کم‌رنگ است. گزارش هفتگی اختیاری و برجسته است.
- پایان ماه: اطلاع‌رسانی؛ فهم از آخرین گزارش هفتگی؛ اگر هدیه تمام شده checkout از همان‌جا (PROG-07 → LIFE-08). یادداشت چرخه بعد می‌ماند.

## 10.1 Launch customer, funnel, catalog bar, and live drift

The first 100 users are adults 18+ on either product version (`ir` or `intl`)
who arrive at the site, create an account, pass safety screening, add a payment
method, and receive one gifted monthly plan. Cycle 2 is paid. IP chooses the
version once at signup; it is not a geo-block.

```text
site (IP → fa+IRR or en+USD)
  -> sign-up -> confirm email
  -> persist profiles.product_region from signup IP; never update from later IP
  -> basics (DOB, residence as profile data)
  -> stop if under 18
  -> safety exclusions
  -> stop before extra health data if ineligible
  -> consent -> goal -> food -> training -> body
  -> payment method (SetupIntent / $0; not charged)
  -> D1 gift reserve -> one monthly generation
  -> wait screen (queue + rotating copy + 3-minute timeout + retry)
  -> Today/Plan daily slice
  -> optional quiet daily check-in; optional bold weekly report
  -> last weekly report informs gift ending → checkout if unpaid
  -> cycle 2: charge monthly subscription, then generate next month
```

Catalog v2 bar before public generation:

- allergens covering milk, egg, peanut, tree nut, wheat/gluten, soy, fish,
  shellfish, sesame, with FA/EN aliases and populated `ingredient_allergens`;
- ~40+ foods across breakfast, lunch, dinner, snack, and portable slots;
- ~20+ exercises with substitutions and used contraindication tags;
- reviewed catalog release, never model-invented IDs.

Until rewrite, live alpha code may still show the older business. That is drift:

| Live drift | Contract |
| --- | --- |
| 7-day trial entitlement | D1 first monthly cycle gift |
| Core/Pro price rows and coach quotas | D4 one subscription |
| `generate-plan` with client `days` 3–14 | one monthly combined plan, `ready_at`, daily slices |
| `analyze-body-composition` | D6: no separate body-report AI |
| Free-text allergies → 409 | D11 picker |
| `admin_review` as the only verification path | D8 payment-method country |
| Empty `AI_ALLOWED_BILLING_COUNTRIES` / IR fail-closed | D12: no geo-block; `product_region` sticky locale+currency |
